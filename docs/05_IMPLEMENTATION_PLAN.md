# 实施计划（IMPLEMENTATION_PLAN）


版本：V0
目标：让 Codex CLI 以可审查、可测试、可回退的方式完成完整训练模式，而不是一次性生成难以维护的成品。


## 1. 开发方式


每个阶段统一执行：
1. 阅读 AGENTS.md 与 docs 中全部规格。
2. 检查当前项目和上一阶段结果。
3. 用中文简述本阶段方案、将修改的文件和风险。
4. 只实现本阶段范围。
5. 运行自动测试、npm run lint、npm run build。
6. 自查浏览器流程和关键状态。
7. 汇报修改文件、实现内容、命令结果、已知问题和下一步建议。
8. 等待用户验收，不自动 Git 提交。


任何规则冲突或规格空白都必须停止相关实现并提出精确问题，不得自行创造关键规则。

## 3. 引擎建模原则


### 3.1 分层事件
不得把“技能、行动、攻击、伤害”写成同一个函数中的大量条件分支。建议使用明确上下文：
- SkillContext：本次技能唯一 ID、施法者、分支、目标、技能内触发锁。
- ActionContext：本次行动与个人回合信息。
- AttackContext：本次攻击的目标、是否命中、普通伤害与附带效果。
- DamageEvent：普通、额外或护盾值伤害。


### 3.2 指令驱动
UI 只派发高层指令，例如：
- SELECT_SKILL
- SELECT_BRANCH
- SELECT_TARGET
- CONFIRM_ACTION
- CANCEL_SELECTION
- END_TURN
- PAUSE_BATTLE
- RESET_BATTLE
- END_TRAINING


核心引擎校验指令是否合法，并返回新状态和事件日志。


### 3.3 确定性
除随机目标与暴击外，相同输入必须得到相同输出。随机数通过依赖注入；测试使用固定序列，实际游戏使用浏览器随机数。


### 3.4 状态批次
普通 Buff/Debuff 使用批次数组保存：来源、效果值、层数、获得时点、剩余回合、是否可叠加。UI 使用 selector 聚合总效果，不破坏批次数据。


### 3.5 触发保护
每次技能拥有唯一 skillExecutionId，并保存“本技能已触发的每目标限制”，用于：
- 势压对同一目标一次。
- 严岩守势一个技能一次。
- 防止自动技能递归。


## 4. 阶段划分

- lint、build 通过。

## 阶段 1｜测试工具与核心类型


任务：
- 检查现有依赖。
- 若无测试工具，提出添加 Vitest 的最小依赖方案并等待用户许可。
- 建立核心类型、数值精度工具、可注入随机数与基础测试。
- 定义角色、位置、阵营、体系、伤害类型、状态批次、技能上下文、战斗阶段。


禁止：
- 暂不做 UI。
- 暂不实现具体角色技能。


验收：
- 整数四舍五入和小数保留一位测试通过。
- 类型检查、lint、build 通过。


建议提交：feat: add battle domain model


## 阶段 2｜行动序列与个人回合


任务：
- 实现行动序列开始、速度读取、稳定同速排序。
- 实现个人回合开始/结束阶段。
- 实现行动与回合分离、一回合多次行动、主动结束回合。
- 实现死亡跳过与新行动序列重新排序。


验收：
- 玩家同速排序为前1、前2、后1、后2。
- 敌方同速 Boss 优先，召唤单位按出场顺序。
- 死亡单位即时跳过。

## 6. 失败保护


- 每阶段验收后再创建 Git 提交。
- 大改前保持工作区干净。
- Codex 修改超出阶段范围时，先查看 git diff，不要盲目接受。
- 若测试失败，优先修复根因，不得删除测试或降低断言来获得绿色结果。
- 若实现与规格冲突，以用户最新确认和原始设计为准，代码必须调整。
